## 一、仓库结构

```
ha-whu-meter/
├── custom_components/whu_meter/      # 集成本体，HACS / GPM 识别此目录
│   ├── manifest.json                 # 集成清单（含 version，发布脚本自动同步）
│   ├── __init__.py / const.py / api.py
│   ├── config_flow.py                # 配置向导与选项流
│   ├── sensor.py / binary_sensor.py  # 六个实体
│   ├── automation.py                 # 余额过低邮件自动化的生成与维护
│   ├── email_template.html           # 告警邮件模板（token 占位符）
│   ├── strings.json / translations/  # 界面文案
│   └── brand/                        # 集成图标（HA 2026.3+ 本地品牌图）
├── docs/                             # 用户使用说明、本文档
├── scripts/release.py                # 一键发布脚本（纯标准库，跨平台）
├── hacs.json                         # HACS 元数据
├── .github/workflows/validate.yml    # HACS + hassfest 自动校验
├── .gitignore / .gitattributes
└── LICENSE                           # MIT
```

代码只依赖 Home Assistant 内置库（`aiohttp` / `voluptuous` 等由 HA 提供），
`manifest.json` 的 `requirements` 为空，无需额外 pip 包。

## 二、HACS / GPM 合规要点

HACS 收录与识别的要求由 `.github/workflows/validate.yml` 在每次推送后自动校验：

| 项目 | 要求 | 本仓库 |
|---|---|---|
| 仓库可见性 | 必须公开 | 公开 |
| 仓库描述 | 需填写 description | 已填 |
| Topics | 至少包含 `home-assistant` | 已加 |
| README | 根目录 README.md | 已备 |
| `hacs.json` | **仓库根目录**，至少含 `name` | 已备 |
| `manifest.json` | 含 `domain` / `name` / `version` / `codeowners` / `documentation` / `issue_tracker` / `integration_type` / `iot_class` | 已备 |
| LICENSE | 根目录许可证文件 | MIT |
| Release | **必须有 GitHub Release**（只打 tag 不算），最新 Release 的 tag 决定 HACS 显示的版本号 | 由发布脚本创建 |

GPM 复用同一套目录规范（仓库根目录下的 `custom_components/<domain>/`），
因此**无需为 GPM 做额外配置**：GPM 会 clone 仓库并软链到 `custom_components/`，
按 tag / commit 判断更新。前端资源才需要 `{{ version }}` 占位符，本仓库不涉及。

> 注意：HACS 的版本号取自**最新 Release 的 tag 名**，所以发版必须同时创建 Release，
> 只推 tag 不会让 HACS 看到新版本。

## 三、发布流程

推荐使用交互向导（不带参数运行）：

```bash
python scripts/release.py
```

1. **选择新版本号**：基于 git 上最新 tag 给出主版本 / 次版本 / 修订号三种递增方案，
   也可自定义输入（如 v1.1.5 -> v2.0.0 / v1.2.0 / v1.1.6）；
   另可选 **5) 补发布**：为已存在的 tag 补发 Release（不改版本号、不建 commit），
   用于发版中断（如网络异常）后的重试
2. **工作区检查**：列出未提交文件（已暂存 / 未暂存 / 未跟踪），可选
   合并提交（并入发版 commit，未跟踪文件需自行处理后继续）/ 撤回（丢弃，需二次确认）/
   stash 保留（发版结束后自动复原）
3. **发版 commit**：选择是否同步「用户使用说明.md」（页首适用版本 + 页尾版本字样），
   与 manifest.json 一并提交为 `chore(release): bump version to vX.Y.Z`
4. **打 tag**：自动在发版 commit 上打 tag
5. **发布**：编写 Release notes（自动生成 / 手动 / 混合），支持先 dry-run 预览再按预览执行；
   发布同时推送发版 commit 与 tag，创建 / 更新 Release 并上传 `whu_meter_vX.Y.Z.zip`

熟练后可用命令行模式（要求工作区干净）：

```bash
python scripts/release.py v1.1.7 --notes "说明" [--no-doc] [--dry-run]
```

首次使用前，将 GitHub PAT（repo 权限）写入仓库根目录 `.github_token` 文件，
或设置环境变量 `GITHUB_TOKEN` / `GH_TOKEN`。

## 四、Python 3.13+ 的 TLS 证书问题

Python 3.13 起 `ssl.create_default_context()` 默认启用 `VERIFY_X509_STRICT`，
会额外要求证书链上每个 CA 证书都携带 `authorityKeyIdentifier` 扩展。
部分 Windows 证书库（以及本地代理软件自签的根证书）不满足该要求，
直连 `api.github.com` 时会报：

```
[SSL: CERTIFICATE_VERIFY_FAILED] certificate verify failed: Missing Authority Key Identifier
```

脚本会自动关闭这一项额外的严格扩展检查（**证书链与主机名校验仍然开启**），
失败时回退尝试 `certifi` 的 CA 包，仍不行则提示设置 `SSL_CERT_FILE`。
此问题只影响发布脚本的 API 调用，不影响 `git push`（走 SSH）。

## 五、网络通道与代理拦截

脚本调用 GitHub API 时按以下顺序自动尝试，任一通道拿到正常响应即停止：

1. **直连**（不使用代理，超时 25s）
2. **系统代理 / 环境变量**（`HTTPS_PROXY` 或 Windows 注册表中的系统代理，超时 120s）

之所以优先直连：本机若运行开发代理 / 加速软件（如 DevSidecar，通常把自己设为系统代理，
端口形如 `127.0.0.1:31181`），它可能拦截 `api.github.com` 并返回自己的 500 错误页
（响应体含 `DevSidecar Error` / `DS-Interceptor`），此时直连反而是通的。
**HTTP 5xx 会被视为通道故障并自动切换下一条通道**；4xx 属于接口的正常应答，不会重试。

## 六、手工发布（不使用脚本时）

```bash
# 1. 同步版本号（两处：manifest.json 的 version、使用说明的页首/页尾）
# 2. 提交并打 tag
git add -A && git commit -m "chore(release): bump version to v1.1.7"
git tag v1.1.7 && git push origin main && git push origin v1.1.7
# 3. 打包（zip 内路径需为 custom_components/whu_meter/...）
#    然后到 Releases 页面手动创建 Release 并上传 zip
```
